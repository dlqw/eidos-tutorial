# 开始前的准备：心智与常见误区

Eidos 的核心产品理念是"**还程序员编码的自由**"：程序员不应为了性能牺牲可读性、可维护性或表达范式，也不应被迫选择特定库、magic number、容器或手工内存策略。递归/迭代、命令式/函数式、高阶类型、模式匹配及自然的数据结构写法都应获得可靠且可预测的编译器优化；内存分配、释放、栈提升、标量化和唯一所有权复用由编译器承担。

带着这个理念开始学习，可以避免三个最常见的误区：

## 误区一：用 Rust/手动内存管理的思维写 Eidos

如果你从 Rust 或 C++ 过来，会习惯性地思考"这个值在堆上还是栈上""谁来释放""要不要 Box/智能指针"。在 Eidos 里这些大多不是你的问题：

- 编译器根据所有权与借用契约自动推导 `ByValue` / `SharedBorrow` / `MutableBorrow` 参数模式，普通 `T` 就是 `ByValue`，`Ref[T]` 是共享借用，`MRef[T]` 是可变借用；
- 编译器承担内存分配、释放、栈提升、标量化和唯一所有权复用；
- `Copy` 不是第四种参数模式：传入 `ByValue` 参数时，编译器根据结构化 `Copy` verifier 与当前 place 状态选择 Copy 或 Move。

你只需要写出意图：`ref expr` 表示共享借用，`mref expr` 表示可变借用，`*expr` 解引用。借用检查、生命周期、冲突诊断都交给编译器，诊断会携带 alias trace 便于定位。

## 误区二：纠结"该选哪个容器"

不要因为底层布局、增长策略或优化路径不同而在多个同类容器/API 之间做编译器本可自动完成的选择。表示选择、专用化和性能策略优先下沉到编译器；标准库提供的是最少且最正交的用户抽象（`Option`、`Result`、`Seq`、`Either` 等），你选语义，编译器选实现。

## 误区三：提前优化

Eidos 的优化发生在编译器里，不发生在你手写 `unsafe` 或手工内存布局里。优先写可直接推断的简单表达式；复杂组合拆成多个 `let`。当性能确实成为问题时，优化的方向是增强编译器，而不是用可读性换性能。

## 本教程不教什么

- 没有智能指针章节（编译器承担内存策略）；
- 没有"选容器"章节（标准库保持最少正交抽象）；
- 性能章节讲的是编译器如何承担优化，以及如何写出可预测性能的代码，而不是手工微操；
- 所有权章节关注借用契约（`ref`/`mref`）与编译器推导，而不是用户手工管理生命周期。

如果某一章感觉"太简单"，那通常不是教程偷懒，而是 Eidos 有意把复杂度收进了编译器。
